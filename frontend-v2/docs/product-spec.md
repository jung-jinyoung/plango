## 1. 주제

### 한 문장

**생산적인 하루를 만들기 위해, 계획하고 실행하고 회고하는 개인 플랫폼.**

### 포지셔닝

> **일정 관리가 본체이고 회고가 부록인 것이 아니라, 회고가 본체이고 일정 관리는 회고할 거리를 만드는 장치다.**

대부분의 플래너는 미래만 본다. 지나간 일정은 흐리게 처리되어 화면 밖으로 밀려난다. Plango는 이 방향을 뒤집는다.

### 설계 원칙

기능 추가가 애매할 때는 **"회고에 쓸 데이터가 남는가"** 로 판정한다.

| 층위     | 내용                                             |
| -------- | ------------------------------------------------ |
| 주제     | 생산적인 하루를 만드는 일정 · 회고 플랫폼        |
| 포지셔닝 | 회고 우선. 계획은 회고의 기준선을 만드는 수단    |
| 기능     | 목표 역산, 텍스트 기반 빠른 입력, 회고 자동 생성 |

**AI 역산의 위치**: 회고가 성립하려면 "계획 대비 실제"를 비교할 기준선이 필요하다. 역산은 회고의 전제조건이며, 전면에 내세우지 않는다.

### 브랜드 해석

Plan + Go에서 **Go는 출발이 아니라 다음 걸음**이다. 한 발로 서서 지나온 걸음을 확인한 뒤 내딛는 한 걸음. 회고 → 다음 계획의 순환과 일치한다.

### 가장 큰 리스크

**회고는 사람들이 원한다고 말하지만 실제로는 하지 않는다.**

대응: **회고는 "작성"이 아니라 "확인"이다.** 자동 포착된 로그에서 AI가 초안을 채우고, 사용자는 틀린 것만 고친다.

## 2. 타겟팅

> **성과가 즉시 드러나지 않는 장기 목표를, 외부 피드백 없이 스스로 관리해야 하는 사람.**

회고 도구가 절실한 사람은 **환경이 피드백을 주지 않는 사람**이다.

해당: 대학원생·연구자, 시험·자격증 준비생, 사이드 프로젝트를 하는 직장인, 프리랜서·1인 창작자

**주 타겟 — 이서연 (27세, 대학원생)**
장기 목표를 스스로 쪼개야 함 / 진도가 안 보여 불안 / 노션과 종이 다이어리로 분리 / 넓은 화면 앞에 오래 앉아 있음

**부 타겟 — 김도윤 (32세, 재택근무 직장인)**
사이드 프로젝트가 있을 때 겹침. 단 실시간 조정 요구가 크고 이는 모바일 중심이라 **1순위로 삼지 않는다.**

**설계에 미치는 영향**: 습관 트래커 기능 없음 / 팀·공유 없음 / 주간·월간 축이 일간보다 중요

## 3. 유저 플로우

### 3-1. 진입 라우팅

위에서부터 먼저 일치하는 하나만 실행. 전부 **기본 도착지**이며 강제 이동이 아니다.

| 순위 | 조건                            | 도착        |
| ---- | ------------------------------- | ----------- |
| 1    | 월간 목표 없음                  | 온보딩      |
| 2    | 새 주 + 지난주 회고 미완        | 주간 회고   |
| 3    | 3일 이상 공백                   | 복귀 리셋   |
| 4    | 오늘 마감 안 함 + **18시 이후** | 오늘의 기록 |
| 5    | 오늘 계획 없음 + **18시 이전**  | 오늘 계획   |
| 6    | 그 외                           | 오늘 뷰     |

### 3-2. 세션

**세션 0 — 온보딩 (60초)**
① 이번 달 목표 1개 입력 → ② AI 역산 4주 제시(수정 가능) ← aha 지점 → ③ 오늘 할 일 확정
**가입은 ③ 이후.** 가치를 보여주기 전 가입 요구는 최대 이탈 지점.

**세션 1 — 오늘 계획 (웹, 3분)**
어제 이월 배너 / 사이드에 주간 목표 잔여 / 텍스트 입력 → 자동 배치 제안 → 드래그 조정 / **"오늘 확정"** → `plannedBlock` 잠금

**세션 2 — 실행 (모바일, 5~20초 × N)**
단일 화면. 완료 / 미루기 / 시간 변경. **드래그 없음.** 완료 체크 시 타임스탬프 자동 포착. 낙관적 업데이트.
넣지 않을 것: 캘린더 전체, 목표 편집, 회고

**세션 3 — 오늘의 기록 (90초)**
자동 포착 값 확인·수정 / 계획 대비 실제 요약 / 미완료 일괄 처리 / 한 줄 메모(선택)
**AI 호출 없음.** 하루치로는 할 말이 없다.

**세션 4 — 주간 회고 (월요일, 3분) ★ 핵심**
① 지난주 실측 ② **미완료 재추정**(6-2) ③ 다음 주 목표 제안 + 가용 시간 검사 ④ 월간 진도 재계산

**세션 5 — 복귀 (공백 3일 이상)**
누적 미완료를 **보여주지 않는다.** 조용히 아카이브 후 "이번 주 목표만 다시 잡을까요?"

## 4. 데이터 계층과 용어집

```
카테고리 ──> 월간 목표 ──> 주간 목표 ──> 할 일
   └──────> 약속 (목표 진도 미포함, 시간만 차지)
```

### 4-1. 용어집 (확정)

**계층**

| 개념      | 코드                 | UI 문구      |
| --------- | -------------------- | ------------ |
| 월간 목표 | `MonthlyGoal`        | 이번 달 목표 |
| 주간 목표 | `WeeklyGoal`         | 이번 주 목표 |
| 할 일     | `Task` (goalId 있음) | 할 일        |
| 약속      | `Task` (goalId 없음) | 약속         |
| 카테고리  | `Category`           | 분류         |

**시간**

| 개념        | 코드            | UI 문구     |
| ----------- | --------------- | ----------- |
| 예상 시간   | `estimatedMin`  | 예상        |
| 계획 블록   | `plannedBlock`  | 계획        |
| 실행 블록   | `actualBlock`   | 실제        |
| 예상 정확도 | `accuracyRatio` | 예상 정확도 |

**상태**

| 코드      | UI 문구       | 금지어             |
| --------- | ------------- | ------------------ |
| `todo`    | 예정          | —                  |
| `done`    | 완료          | —                  |
| `carried` | 다음으로 옮김 | 미완료, 실패, 놓침 |
| `dropped` | 이번엔 안 함  | 삭제, 포기, 버림   |

**세션**

| 시점        | 이름           |
| ----------- | -------------- |
| 아침        | 오늘 계획      |
| 낮 (모바일) | 화면 이름 없음 |
| 저녁        | 오늘의 기록    |
| 월요일      | 주간 회고      |

일간은 **기록**, 주간은 **회고**. 일간에는 해석을 요구하지 않고 사실만 확인시킨다.

**폐기된 용어**: 태그, 실천, 달성률, 독립 일정, 추정 시간, AI 우선순위 분석

### 4-2. 규칙

- **카테고리는 목표에만 붙는다.** 할 일은 상속받으며, 저장하지 않고 읽을 때 파생시킨다
- **약속**은 진도에 안 들어가지만 가용 시간을 차지하므로 역산에 반영한다
- 진도는 개수가 아닌 **시간 기준**
- 주간 목표는 반드시 **산출물 형태**("선행연구 정리 완료"). 완료 판정이 안 되면 회고가 성립하지 않는다
- **주간 목표 직접 생성은 막는다.** 역산이 유일한 생성 경로여야 계층 구조가 화면에서 증명된다

### 4-3. 생성 시점 (Just-in-time)

| 시점           | 생성               | 미생성       |
| -------------- | ------------------ | ------------ |
| 월간 목표 등록 | 주간 목표 4개      | 할 일 없음   |
| 그 주 월요일   | 이번 주 할 일 후보 | 다음 주 이후 |
| 매일 아침      | 오늘 시간블록      | 내일 이후    |

### 4-4. 타입

```ts
type MonthlyGoal = {
  id: string
  title: string
  month: string // '2026-08'
  categoryId: string
  baselineHours: number // 초기 추정, 잠금
  status: 'active' | 'achieved' | 'dropped'
}

type WeeklyGoal = {
  id: string
  title: string // 산출물 형태
  weekOf: string // 해당 주 월요일
  monthlyGoalId: string | null
  estimatedHours: number // 이월 시 재추정
  carryCount: number
  status: 'active' | 'achieved' | 'carried' | 'dropped'
}

type Task = {
  id: string
  title: string
  weeklyGoalId: string | null // null = 약속
  categoryId: string | null // weeklyGoalId 있으면 미사용
  estimatedMin: number
  plannedBlock: { start: string; end: string } | null
  actualBlock: { start: string; end: string } | null
  status: 'todo' | 'done' | 'carried' | 'dropped'
}
```

`resolveCategory(task)` — 목표 체인을 따라가고, 없으면 `task.categoryId`. 값 복사 금지.

## 5. 계획과 실제

### 5-1. 왜 분리하는가

애플 캘린더는 드래그하면 일정 자체가 바뀌고 원래 값이 남지 않는다. 회고를 하지 않는 도구이므로 그것이 맞다. Plango에서 같은 동작을 하면 **비교 기준선이 매번 지워진다.**

### 5-2. 같은 제스처, 시점에 따라 다른 의미

| 대상               | 의미      | 결과                                          |
| ------------------ | --------- | --------------------------------------------- |
| 현재 시각 **이후** | 계획 수정 | `plannedBlock` 변경                           |
| 현재 시각 **이전** | 실제 기록 | `actualBlock` 생성·수정, 계획은 고스트로 잔존 |

**현재 시각 바가 이 규칙을 설명하는 유일한 시각 장치다.** 좌우 끝까지, 충분히 강하게 그린다.

### 5-3. "오늘 확정" = 데이터 무결성 경계선

확정 전에는 모든 것이 유동적, 확정 순간 `plannedBlock` 스냅샷 후 잠금, 그 이후 모든 변경은 실제 기록.

### 5-4. 실제 시간 수집 3단계

수동 입력만으로는 로그가 빈다.

1. **자동 포착** — 완료 체크 시각 기준으로 `actualBlock` 초안 생성
2. **드래그 보정** — 웹에서 과거 블록 조정
3. **일괄 확인** — 오늘의 기록에서 훑고 수정

자동 포착은 부정확하다. **그 부정확함을 고치는 것이 오늘의 기록의 본업이다.**

### 5-5. 표시

- **차이가 15분 이상일 때만** 계획 고스트를 병기
- 고스트 = 점선 테두리 / 실제 = 채움
- 이 화면 자체가 회고다

## 6. 이월과 롤업

### 6-1. 이월은 조정이다

- 빨강·경고색 사용 금지
- "실패", "놓친 일" 사용 금지 → "다음으로 옮김"
- 회고 화면에서 이월은 **계획 조정 내역**으로 묶는다

**예외**: `carryCount >= 3`은 신호다. 비난이 아닌 선택지로 노출한다.

> "이 항목이 3주째 밀리고 있어요. 쪼갤까요, 목표에서 뺄까요?"

### 6-2. 산술 차감이 아니라 재추정

10h 계획에 6h를 썼는데 안 끝났다면 남은 게 4h라는 보장이 없다. **원래 추정이 틀렸다는 증거가 방금 나왔다.**

> 선행연구 정리 — 6h 썼는데 아직 안 끝났어요. 남은 양은 얼마로 볼까요?
> _이번 주 예상이 평균 1.4배 길었어요. 4h로 보면 실제로는 5~6h일 수 있어요._

재추정 자체가 회고이며, **예상 정확도 지표가 여기서 실제 쓸모를 갖는다.**

### 6-3. 과거 불변 원칙

**지난 주 기록은 이동하지도 수정하지도 않는다. 이월은 새 항목 생성이다.**

- 지난주 항목: `carried`로 그 주에 남김
- 다음 주: 재추정 값으로 새로 생성, `carryCount` 승계

### 6-4. 월간 총량은 파생값

`baselineHours`는 잠금. 현재 총량 = 완료 실적 + 남은 주간 재추정 합. 둘의 차이가 **범위가 늘어난 정도**다.

### 6-5. 과부하 방지

```
주간 가용 시간 = 지난 4주 실제 투입 중앙값 − 이미 잡힌 약속
```

사용자 설정값이 아니라 **실측 중앙값**을 쓴다. 사람은 자기 가용 시간을 과대평가한다.

## 7. 입력

### 7-1. 폼을 만들지 않는다

① **캡처** — 텍스트 한 줄 → ② **정리** — 자동 배치 제안 → ③ **편집** — 카드 클릭 시

편집 시 카테고리 필드는 목표 연결이면 **자동 표시 + 비활성**. 목표 드롭다운에는 **이번 주 목표만** 노출.

### 7-2. 텍스트 문법

```
헬스장 운동 45m #운동
```

**토큰의 생김새로 판정한다. 순서 자유.**

| 토큰         | 해석                  |
| ------------ | --------------------- |
| `45m` `45분` | 예상 시간 (15분 단위) |
| `#운동`      | 목표 연결 (자동완성)  |
| 나머지       | 제목                  |

- `#` 없으면 자동으로 **약속**
- 부분 입력 허용
- **번호 참조 금지.** 목표가 추가·삭제·정렬되면 번호가 조용히 어긋나 잘못된 목표에 시간이 기록된다

### 7-3. 예상 시간은 사용자가 입력한다

예상 정확도가 대표 지표이므로 **추정 주체가 사용자여야 한다.** AI가 추정하면 "AI가 얼마나 잘 맞히나"를 재게 된다.

AI는 안 적었을 때만 채우고, 적었으면 힌트만 준다: _"비슷한 일은 지난 3번 평균 50분이었어요"_

### 7-4. 파싱 미리보기

```
[ 헬스장 운동 45m #운동          ]
  헬스장 운동 · 45분 · 운동      ← 타이핑하는 동안 갱신
```

축약 문법은 도움말로 가르치지 않는다. 아무도 읽지 않는다.

### 7-5. 문법에 필드를 더하지 않는다

3개를 넘으면 아무도 외우지 않는 CLI가 된다. 더할 필요도 없다 — 카테고리는 상속, 우선순위는 자동 배치, 마감일은 주간 목표가 한정.

### 7-6. 자동 배치

- **약속을 먼저 고정**하고 그 틈에만 배치. 겹치면 계획이 첫날부터 거짓말이 된다
- **4시간 초과 블록은 쪼개도록 제안.** 회고의 해상도는 블록 크기가 결정한다
- 배치는 항상 제안 상태. "오늘 확정"을 눌러야 커밋

## 8. 지표

**완료율을 헤드라인으로 쓰지 않는다.** 완료율이 대표 지표이면 사용자는 점수를 올리려고 **계획을 적게 세우는 법**을 학습한다.

| 지표             | 위치   |
| ---------------- | ------ |
| 목표별 투입 시간 | 주지표 |
| 예상 정확도      | 주지표 |
| 완료율           | 보조   |

## 9. 디자인 시스템

### 9-1. 방향

토스 스타일 — **단순하고 명료하고 깨끗하게.** 배경은 거의 흰색, 카드는 순백, 테두리 대신 명도 차이로 분리. 그림자는 거의 쓰지 않는다.

**뉴모피즘은 쓰지 않는다.** 명암비가 기준 미달이고, 고밀도 캘린더와 상극이며, 대기 상태에 그림자를 다 써서 드래그 상태를 표현할 여유가 없다.

**회색은 쿨 뉴트럴로.** 웜그레이(베이지 기운)는 넓은 면적에서 바랜 종이처럼 읽힌다.

### 9-2. 색 토큰

```css
--surface-page: #f7f8fa;
--surface-card: #ffffff;
--surface-sunken: #f2f4f6;
--border: #e5e8eb;

--text-primary: #191f28;
--text-secondary: #6b7684;
--text-muted: #8b95a1;

--rose-50: #fff0f4;
--rose-500: #ff4e7e;
--rose-600: #f5326a;
--rose-700: #c81e52;
```

**카테고리 6색 (고정, 로즈 계열 제외)**

| 이름   | 값        |
| ------ | --------- |
| 블루   | `#3182F6` |
| 민트   | `#00BFA5` |
| 앰버   | `#FFA218` |
| 퍼플   | `#7C5CFF` |
| 그린   | `#4ECB71` |
| 그레이 | `#8B95A1` |

사용자는 **이름만 지정**하고 색은 이 6개에서만 고른다. 자유 색상은 명암비와 구분성을 무너뜨린다. 로즈 계열을 뺀 이유는 카테고리 색과 액센트 색이 같은 계열이면 "분류인지 선택 상태인지" 구분이 안 되기 때문이다.

### 9-3. 로즈 사용 허용 목록

**허용**: 현재 시각 바 + 플라밍고 / 주 CTA(화면당 1개) / 선택·포커스 / 로고
**금지**: 카드 배경, 헤더, 내비게이션, 일반 아이콘, 링크 텍스트, 카테고리 색

`rose-50` 배지는 "오늘" 같은 시간 표시에만.

### 9-4. 일정 블록 채색

깔끔함은 여기서 결정된다. 하루 20~30개 블록을 진한 색으로 채우면 반드시 어수선해진다.

```css
background: color-mix(in srgb, var(--cat-color) 10%, white);
border-left: 3px solid var(--cat-color);
color: var(--cat-color-dark);
```

**틴트 배경 + 좌측 3px 컬러 바 + 같은 계열 진한 텍스트.** 진한 색은 3px 바에만 쓴다.

**약속은 회색 틴트에 좌측 바 없음.** 컬러 바가 있는 블록만 눈에 띄어 "오늘 목표에 쓰는 시간"이 저절로 보인다.

### 9-5. 그림자

```css
--elev-rest: none;
--elev-hover: 0 1px 3px rgba(0, 0, 0, 0.06);
--elev-drag: 0 8px 20px rgba(0, 0, 0, 0.12);
```

대기 상태를 0으로 두니 **드래그에 쓸 그림자가 온전히 남는다.**

### 9-6. 밀도 두 스케일

|           | 패널 · 카드 | 캘린더 그리드 |
| --------- | ----------- | ------------- |
| padding   | 20~24px     | 6~8px         |
| gap       | 16px        | 2px           |
| radius    | 16px        | 6px           |
| 최소 높이 | —           | 22px (15분)   |

토스식 여백을 캘린더에 그대로 쓰면 하루에 블록 4개밖에 안 들어간다.

### 9-7. 주간 회고만 다크

주간 회고 화면 전체를 어둡게 한다. 일주일에 한 번뿐인 **다른 모드**임을 배경색으로 알리고, 어두운 배경에서 로즈가 가장 잘 산다. **캘린더 본체는 밝게 유지** — 조밀한 그리드에 작은 텍스트가 많으면 어두울 때 가독성이 떨어진다.

### 9-8. 로고

전체 모습은 세로로 길어 정사각 아이콘에 안 맞고, 다리가 얇아 24px 이하에서 사라진다.

**포즈 2개 시스템** — 플라밍고의 실제 자세 두 가지가 제품의 두 모드와 대응한다.

- **한 발로 서서 앞을 봄** → 계획, 실행
- **목을 뒤로 접어 등에 얹음**(실제 휴식 자세) → 회고

| 크기    | 형태                           |
| ------- | ------------------------------ |
| 16~32px | 목 S커브만                     |
| 40~96px | 실루엣 (몸통 + 목 + 다리 하나) |
| 120px+  | 2포즈 캐릭터                   |

- **단색 로즈만.** 로고가 색 규칙의 예외가 되면 나머지도 무너진다
- **표정 없음.** 눈코입이 들어가면 포즈 2개로 끝날 일이 12개가 된다
- **화면당 그래픽 1개.** 현재 시각 바에 플라밍고가 있으면 그 화면 다른 곳엔 넣지 않는다

**주 활용처**: 현재 시각 바 마커(시간이 흐르면 타임라인을 따라 내려감) / 주간 회고에서 회고 포즈로 전환 / 빈 상태 / 로딩(S커브가 그려지는 애니메이션)

## 10. 문구 규칙

### 10-1. 기본

- **해요체로 통일.** 상황·맥락 불문
- **능동형** 우선 ("됐어요" → "했어요")
- **긍정형** 우선 ("없어요" → "~하면 할 수 있어요")
- 과도한 경어 배제 ("~시겠어요?" → "~할까요?")
- 명사+명사 조합 지양 (한자어는 풀어쓰기)
- 다이얼로그 왼쪽 버튼은 **"닫기"**. "취소"는 작업이 취소된다는 오해를 부른다

### 10-2. 상태별 문구

| 상황        | 쓰지 않을 말           | 쓸 말                                                      |
| ----------- | ---------------------- | ---------------------------------------------------------- |
| 이월        | 미완료, 실패           | 다음으로 옮겼어요                                          |
| 제외        | 삭제, 포기             | 이번엔 안 하기로 했어요                                    |
| 목표 없음   | 목표가 없습니다        | 목표를 정하면 일정을 짜드릴게요                            |
| 회고 미작성 | 회고를 하지 않았습니다 | 이번 주 기록을 확인해볼까요                                |
| 공백 복귀   | 5일간 기록이 없습니다  | 지난 5일 기록이 비어 있어요. 이번 주 목표만 다시 잡을까요? |
| 초과 경고   | 시간이 부족합니다      | 남은 2주에 14시간이 필요해요. 범위를 줄일까요?             |

**이월을 조정으로 취급하기로 한 결정과 긍정형 원칙은 같은 방향이다.** 하나만 지키고 다른 하나를 어기면 어색해진다.

## 11. AI 통합

**AI는 상태를 직접 변경하지 않는다. 제안 → 사용자 수락 → 상태 변경.**

호출이 실패해도 제안 카드가 안 뜰 뿐 앱은 정상 동작한다. 출력은 스키마 검증(zod) 후 실패 시 규칙 기반 폴백.

| 함수                   | 입력                                      | 폴백                    |
| ---------------------- | ----------------------------------------- | ----------------------- |
| `decomposeMonthlyGoal` | 목표 + 마감 + 카테고리                    | 4주 균등 분배           |
| `suggestDayLayout`     | 인박스 + 약속 + 주간 잔여 + **실측 평균** | 마감일 순 배치          |
| `weeklyReflect`        | 실측 + 예상 정확도                        | 미달성 항목 그대로 이월 |

프롬프트는 함수당 파일 하나로 분리한다.

## 12. 범위 (포트폴리오 · 기한 있음)

**필수**
온보딩(목표 1개 → 4주 역산) / 텍스트 입력 + 파싱 미리보기 / 주간 목표 뷰 + 오늘 뷰 + **계획·실제 병기** / 모바일 실행 뷰 / 오늘의 기록 / 주간 회고 → 재추정 → 다음 주 목표 제안 / **시드 데모 계정 3주치**

**여유 되면**
드래그 재배치 / `carryCount >= 3` 감지 / 가용 시간 초과 경고

**제외**
월간 회고 리포트 / 달성률 대시보드 / 태그 역추적

**시드 스크립트는 개발 초기에 만든다.** 없으면 주간 회고 화면을 재현할 수 없어 차별점의 절반이 화면에 안 나타난다.

## 14. 폴더 구조

```
src/
  app/                  # 라우팅만. 로직 없음
    onboarding/
    today/              # 오늘 뷰 · 오늘 계획
    week/               # 주간 목표
    reflect/            # 오늘의 기록 · 주간 회고
    m/                  # 모바일 실행 전용
  features/
    goal/               # 월간 · 주간 목표
    task/               # 할 일 · 약속 · 입력 파서
    schedule/           # 캘린더 · 블록 배치 · 드래그
    reflect/            # 기록 · 회고 · 재추정
    ai/                 # 프롬프트 · 스키마 · 폴백
  entities/             # 타입, 도메인 규칙 (resolveCategory 등)
  shared/
    ui/                 # 디자인 시스템 컴포넌트
    lib/
    styles/tokens.css
```

**경계 규칙**: `features/*`는 서로 직접 import 하지 않는다. 공유가 필요하면 `entities` 또는 `shared`로 내린다. 이 규칙 하나가 나중에 스파게티를 막는다.
